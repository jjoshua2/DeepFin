# Tri-source replay storage checkpoints and one BT4 compression slice

**Diagnostic readout, 2026-09-30; zero corpus, target and throughput credit.** The earlier 83,991-row strict replay stored two complete 44,800-byte canonical-input waves before exact byte/order comparison and global duplicate resolution. Each wave occupied 3,762,796,800 bytes; together they occupied 7,525,593,600 bytes. The later full-pack row JSON index was 68,624,951 bytes for 83,416 winners. The replay resolver also materializes global UID sets, digest groups and a winner list, while the pack materializes source/target joins and game-ID rosters. These current diagnostics cannot be made 500M-ready by changing only the physical ZIP shard size.

A CPU-only paired-wave segment prototype sealed 8,192-row segments with 512-row zstd frames and local UID-prefix tables. On an **8,193-row, 64-byte synthetic fixture**, the first segment survived a deliberate SIGKILL immediately after its atomic seal; resume verified and skipped it. A later-segment byte-identical duplicate won by the unchanged global UID-rank rule. The fixture refused a conflicting context, a changed second-wave native byte, a changed input pin, a corrupted compressed frame, a truncated or relinked second-wave comparison receipt, a forged paired-row digest and optimized Python mode. The corrected archived fixture was rerun from an isolated directory containing only its v2 source. Its zstd ratio applies only to generated 64-byte rows. The current strict source child does not yet resume at an archive/game cursor or carry per-game proof and Syzygy-inventory pins in each row; the prototype is not a replacement for it. Its wall/RSS checks are cooperative, so a production caller would require an owned per-segment kill-and-reap watchdog.

The bounded probe was registered as a lossless zstd level-5 size measurement on one 8,192-row source slice, with exact per-row digest, proof and route checks, a 600-second owned-process watchdog, a 2 GiB address-space/RSS cap and a 512 MiB output cap. A failed exact-byte or independent readback would have withheld the size result. No target or training comparison was planned.

We then measured one **already banked BT4-v9 gross-candidate slice**, ordinals 0–8,191 of the first strict replay wave. Its 367,001,600 native bytes produced 4,329,582 bytes of zstd level-5 DATA in sixteen independent 512-row frames; with the 1,280-byte frame index, the retained data/index subtotal is **4,330,862 bytes** (528.67 bytes per gross row). The 84.77× ratio is **DATA bytes only** for this BT4 slice. The operator pinned the complete replay receipt, index, game-history proof, teacher-route contract and strict Syzygy inventory; checked each selected native row against its indexed byte and domain digests; and joined all selected UIDs to their game-history proof. Teacher routes counted 4,146 BT4 and 4,046 Ceres. A separately authored direct reader then matched all 8,192 source rows and sixteen frames, including the index, history proof and teacher join, without importing the producer. The author process took 2.417 seconds wall and 2.392 seconds CPU with 171.5 MB peak RSS; it used a bounded cached local slice, so these times are not external-drive or training throughput measurements.

This slice does not measure Ceres or SF source compression, the second replay wave, candidate metadata, selected raw-head banks, trainer ZIPs, target joins, external-drive loading, or GPU training. In particular, the 4,330,862-byte subtotal excludes UID/context/provenance/proof tables, the original source bank, claim/receipts and independent proof copies. The synthetic prototype's verbose per-row JSON metadata was 4,544,340 bytes for 8,192 tiny rows, plus a 131,072-byte row index. Compressed DATA alone is therefore not a whole-corpus storage forecast.

A proposed next format uses 100-byte fixed candidate records with segment-local exact UID/context/proof/provenance tables and checkpointed external UID and input-digest sorts. Those sorts would enforce global UID uniqueness, byte-exact digest-group and context comparison, the existing UID-rank winner, deterministic game IDs and exact target joins without a monolithic winner JSON receipt. This is a design and CPU-fixture plan, not implemented production behavior. Each source segment and merge output needs an atomic input/config-bound receipt, an archive/game replay cursor and an owned <=10-minute watchdog. A banked representative source run and independent all-field readback are required before any storage or throughput projection to 500M.

A subsequent **CPU-only 8,193-row synthetic external-join fixture** exercised the proposed 100-byte candidate record with exact segment-local UID, context, proof and provenance tables. Its two source segments (8,192+1 rows) fed at-most-2,048-row initial UID/digest sort runs and at-most-four-way merges. The first merge process was killed with SIGKILL immediately after its first atomic seal; resume reused that verified seal, and a no-op rerun left all 49 receipts unchanged. The author-written harness checked 18 refusal cases and compared winner UID, ordinal, outcome, teacher, packed game ID and target SHA tuples against a bounded reference. The root operator reran that same harness and matched its manifest SHA; this was a reproduction of author checks, **not a separately authored byte audit**. The fixture uses generated 64-byte native rows and still caches its two segments and buffers bounded JSON outputs. It has no archive/game source cursor, production native-frame or Syzygy binding, trainer-pack parity, external-drive result or 500M-capacity credit.
