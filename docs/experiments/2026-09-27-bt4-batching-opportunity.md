# BT4 run11 variable-batch scheduling opportunity

**Source-only readout, 2026-09-27.** The completed BT4 full-prefix pilot emitted 453,108 positions from 4,096 complete games in 15,387 physical model calls. Its effective batch sizes ranged from 1 to 64. This is call-count evidence, not a measured GPU wall improvement or admitted 500M throughput; source, target, corpus and owner credit remain zero.

## Why calls were small

The worker starts 64 consecutive games and finishes the entire wave before admitting the next 64. Each call evaluates one root from every unfinished game. Game lengths vary from 7 to 342 emitted rows, so late calls in each wave become small. The saved per-game lengths reproduce all 64 bins of the physical-call histogram: 5,329 calls had at most eight rows, carrying only 15,672 positions (3.46% of the total). The previous fixed-32 utilization estimate was invalid; 6,933 observed calls already exceeded 32 rows.

With a 64-root limit, 453,108 fixed evaluations require at least **7,080 calls** by capacity alone. An immediate-replacement simulation over the unchanged per-game lengths uses **7,193 calls**, versus 15,387 observed. This is conditional arithmetic: changing the schedule can change model batch shape, floating output, sampled moves, game length, Syzygy timing and file bytes. It cannot be counted as an 8,194-call saving or a wall-speedup. The later 128-ID exact-output check failed, as recorded below.

## Original bounded comparison

The first two fixed waves, game IDs 0–127, contain 14,253 rows and used 396 calls. A virtual immediate-replacement schedule predicts 320 calls if their individual game traces remain unchanged. At this record's original readout, the full-prefix worker and strict replay verifier admitted only 4,096-game primary or 1,024-game top-up banks; a separately reviewed 128-ID diagnostic runner and verifier were required.

The planned comparison used sequential sole-GPU A and B arms on the same 128 IDs, model, seed, full histories and 64-root cap. It required each per-game NPZ SHA-256 to match the original sealed run11 subset, plus keyed feed, raw legal-logit and WDL bytes, complete all-attempt strict replay, each arm's own full physical-call ledger, and rule50-aware six-man Syzygy WDL/DTZ parity. The ledger stream hash could differ by design as call rosters changed. Only after parity could wall, inference, writer and tablebase timings be compared. Any changed game or target would make it a different scientific comparison.

## 2026-09-28 diagnostic result and next cost question

A separately reviewed 128-ID ABBA diagnostic was implemented and launched, but it stopped in B1 with `QUARANTINED_ZERO_CREDIT`. A1 passed worker, strict replay and physical-call readback: all 128 game NPZ hashes matched the frozen roster, with 396 calls and 14,253 slots. B1 wrote 128 games, but 83 NPZ hashes differed. Its **unsealed** `.writing` ledger contains 320 calls and 14,252 slots; B2 and A2 did not run. This is neither a complete A/B timing result nor a measured source-wall speedup. The one-shot authority is spent; any further physical run requires new reviewed source and launch gates.

The independent [read-only forensic record](evidence/2026-09-28-bt4-immediate-refill-128-forensic.json) (SHA-256 `53c76c153231f8a3e80d4aa025df26f8d928a08083b11b5fac32f57d43b75d3c`) found 45 byte-identical games, 82 with unchanged trajectory but changed policy and/or WDL, and one changed trajectory. For game 108 at row 137, the input and pre-move context match, but A1 chooses `d5c5` and B1 chooses `d5e5`. The same seeded draw falls between their two policy cumulative probabilities, so B1 has one fewer row. The physical batches differ at that position (11 versus 9 roots), consistent with batch-dependent numeric output; the evidence does not isolate a particular provider kernel. The exact-game and exact-target parity requirement failed. The v7 source packet SHA-256 is `19c3c444061b4cb0092eeff95b5e1c4ccfc4aa73d1613e7b2c2de6528a33c2a5`; its independent source review SHA-256 is `7b0444fade075ff03c8cdd1e8e729b306b63846d461d38afa9fa9bbde55cc3a8`; the quarantined terminal SHA-256 is `68f70fab70b196ac0b685f719958264c7a846a9855711732948f0cf0a7694867`.

If scheduling cost remains the question, the smallest new test uses the **same frozen 14,253 A1 position inputs** without sampling moves or generating games. Before GPU use, independently reconstruct and hash every keyed `(game_id, ply_index)` feed, then freeze the original 396-call wave partition and a 320-call immediate-refill partition derived from A1's fixed game lengths. Both must cover each identical feed exactly once, with 1–64 real roots per call. A separately reviewed, bounded A1/B1/B2/A2 fixed-input screen could compare paired inference and total pipeline wall, call-size histograms and per-key numeric drift; it should preregister a cost threshold and stop on any feed mismatch. It would answer inference scheduling cost only, with zero corpus, target and owner credit. It cannot establish full 4,096-game wall savings.

Immediate refill could instead be studied as a **different game-generation policy**, since its batch-dependent outputs change training examples. That requires its own complete strict bank/readback and downstream quality or strength evaluation. The present result rules out promoting it as a byte-preserving optimization of run11.
