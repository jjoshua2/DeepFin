# Bounded checkpointed sort foundation for tri-source metadata

**CPU-only implementation and synthetic validation, 2026-09-30; zero corpus, target, and throughput credit.** The [storage readout](2026-09-30-tri-source-storage-checkpoints.md) found that compressing canonical input bytes alone leaves global candidate metadata, duplicate resolution, and target joins unbounded. This change implements a reusable fixed-record metadata segment and external-sort primitive in [`checkpointed_sort.py`](../../chess_anti_engine/source/checkpointed_sort.py). It does not connect them to the live replay or admit a trainer pack.

Each independently sealed candidate segment holds at most 8,192 fixed 100-byte records plus exact segment-local UID, context, proof, and provenance tables. Its claim binds source, config, native-source, and code SHA-256 identities. Source sort runs hold at most 2,048 rows and a configured byte cap of at most 8 MiB; merges use at most four inputs and seal physical output parts with input cursors and a chained receipt. Stable ordering includes the global input index. A digest-group fold retains only the first exact native/context pair, the current minimum rank, counts, and outcome histogram while streaming losers to a caller. An owned CPU subprocess helper caps address space and kills and reaps its process group after at most 600 seconds.

The focused Python 3.10 suite passed five tests. It exercised 8,193 identical-digest rows with a bounded accumulator; stable multiway merge; changed claim, cursor, part, and segment refusals; and two real child SIGKILL boundaries. One kill followed the first sealed merge part. The other occurred after `.RUN.json.part` was fsynced but before it became `RUN.json`: resume removed only that owned unsealed scratch file, kept the sealed part receipt bytes unchanged, and finalized the run. A scratch file beside an already sealed final receipt was refused. A no-op replay preserved the final receipt SHA-256.

The current full-repository type gate remains nonzero with the existing Python 3.10 environment. Under the same temporary dependency overlay, the exact pre-change base commit and this branch produced **the identical 188 errors and 8 warnings** by relative file, line, and diagnostic message; the new module and tests produced zero. Focused Ruff, Vulture at the repository's 80% threshold, and Pyright checks passed. This comparison establishes no new type diagnostics; it does not claim a clean repository-wide lint gate.

Recursive verification still scans ancestor runs repeatedly. In a synthetic fan-in-four hierarchy of 64 one-row source runs, first construction invoked full part verification 519 times and visited 90,648 bytes of part payload extents; a no-op replay invoked it 477 times and visited 75,540 bytes. The final run itself held 5,036 bytes, so even no-op verification revisited 15 times that extent before counting the separate hash and row-parse reads. These tiny synthetic ratios do not predict 500M-row runtime. A production restart could spend its entire 600-second unit limit validating old ancestors before reaching its last output cursor. Bounded, resumable verification requires content-hash checks tied to independently immutable or versioned physical parts; without that storage contract, old bytes must be rehashed.

Production integration remains separate: two canonical waves must be sealed and compared byte-for-byte in order before global winner selection; archive/game cursors, exact native-byte proof, game history and Syzygy inventory, teacher and target joins, source-qualified game IDs, and all-15-array trainer-pack readback must be bound to the resulting receipts. The [evidence index](evidence/2026-09-30-tri-source-checkpointed-sort-foundation.json) pins the frozen source, test, crash-fix patch, synthetic scaling result, and matched type diagnostics. No bulk corpus or GPU work was used.
