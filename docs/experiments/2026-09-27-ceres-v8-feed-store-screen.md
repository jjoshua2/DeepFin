## Exact seam and bound

`ledger_readback.collect_row_feeds` reconstructs every accepted `(64,137)` uint8 TPG feed from stored `x`, adds discarded trace feeds, checks SHA/duplicate keys and all-attempt counts, then retains each 8,768-byte feed in one `dict[(game_id, ply_index)]` for `verify_saved_ledger`. This is a memory-headroom seam. The verifier only calls `row_feeds.get(key)`, iterates keys with `set(row_feeds)`, and calls `len(row_feeds)`; it checks each returned raw feed's length and SHA, the call's physical bytes and padding, and the final all-attempt census. A lazy `Mapping` can therefore supply exact `bytes` to that consumer, provided the original array schema/source/duplicate checks remain before insertion. The candidate validates raw length and SHA, rejects duplicate keys and a bounded encoded-payload budget, stores each digest with a level-1 zlib payload for feeds with at least 75% zero bytes, falls back to exact raw bytes otherwise, and bounds/rehashes every decoded feed. It has no bank reader or v8 integration.

The v8 plan caps the primary at 2,048 games and 400 plies/game: 819,200 possible all-attempt feeds, or 7,182,745,600 bytes (6.69 GiB) of *raw feed payload alone*. The operator applies `max_child_rss_bytes=12,884,901,888` (12 GiB) and a 32 GiB available-RAM floor to the ledger-readback child every 0.5 s. At the same row count, the candidate's incompressible fallback would charge 7,209,779,200 bytes for payload plus stored 32-byte digests and one accounting byte per row, before Python dict/key/tuple objects, zarr/ZIP buffers, transient arrays and readback work. The payload cap is **not a process RSS cap**; even periodic RSS checks can miss transient peaks. No feasible worst-case 12 GiB guarantee follows from favorable TPG compression ratios. A real integration would need an explicit total row/object bound and measured peak process RSS under the frozen stage maximum, or a separately reviewed streaming/sharded verifier design.

## Bounded measurement

I ran each variant in a separate `nice -n 15` process with `CUDA_VISIBLE_DEVICES=''`, `OPENBLAS_NUM_THREADS=2`, and `OMP_NUM_THREADS=2`; three repetitions per cell, 8,192 distinct feed objects/keys per run. `sparse` uses 128 locally encoded legal-chess TPG templates (zero fraction 87.6–91.2%) and `incompressible` uses 128 deterministic pseudorandom byte templates. No registered bank, model, ONNX session, GPU, or external archive was read. The benchmark times insertion with per-row SHA and complete physical-call-style `.get`/SHA/stream-hash/census lookup; it records current and peak RSS and shallow Python dict/key/tuple/bytes accounting. The following are medians, not full-path wall:

| Feed / store | Build s | Lookup s | RSS after build MiB | Payload MiB | Shallow Python MiB |
| --- | ---: | ---: | ---: | ---: | ---: |
| Sparse / raw dict | 0.128 | 0.116 | 106.26 | 68.50 | 69.91 |
| Sparse / adaptive compression | 0.307 | 0.265 | 44.28 | 5.19 | 7.35 |
| Incompressible / raw dict | 0.121 | 0.117 | 106.01 | 68.50 | 69.91 |
| Incompressible / adaptive compression | 0.166 | 0.153 | 107.03 | 68.76 | 70.92 |

The sparse candidate saves about 62 MiB measured RSS per 8,192 rows while adding about 0.33 s to build plus lookup. Incompressible fallback is about 1 MiB larger and 0.08 s slower than raw; compression does not improve throughput here. The outer physical-feed SHA-256 matched between stores: sparse `5726a25c9353ffe6a3c8c036a13737517f5e58f8f64afa53a58f652f51648988`, incompressible `b5a7c6e00c05222b37c9c7e1be4c31f9e95cc68deeffe24c27b3a64dfe87de5e`. Shallow Python accounting is diagnostic and omits interpreter/allocator internals; RSS is the actual process measurement. The synthetic rows repeat 128 templates, omit ZIP/zarr materialization and JSON ledger parsing, and cannot establish v8 peak RSS or a full-path rate change.
