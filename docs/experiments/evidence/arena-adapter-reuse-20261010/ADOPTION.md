# Future-launch adoption procedure

This is a source preparation procedure, not launch authorization. Do not execute
an arena, probe or acquire a canonical lease, change a control marker, or update
the existing armed evaluation while following the preparation steps.

1. Start from a separately authorized future evaluation. Preserve the exact plan,
   model/checkpoint and inference references, panel, config/tablebase catalog,
   source seal dependencies, search settings, pair count, time/session limits and
   process/lease ownership contract applicable to that evaluation. This packet is
   specifically the frozen short-E/fresh 2,606-pair route; it does not authorize
   changing that science contract or running a different route.
2. Copy the two candidate production files into a new code-only runtime directory,
   keeping `short-e-evaluation-owner-v4/arena_phase_adapter_pair_bound_v4.py`
   relative to the fresh wrapper. Preserve exact bytes; the embedded shared hash
   must match. Keep the previously reviewed historical shim, serving source and
   overlay paths bound to their original identities. If those dependencies no
   longer exist, hold preparation instead of substituting current main code.
3. Create fresh operation/prepared/review records and a fresh external output root.
   Add both the executing wrapper and the shared adapter to the reviewed source-pin
   closure. Bind `arena.adapter_ref` to the actual new wrapper path and hash. Do not
   rewrite an old packet, manifest, source seal, completed pair receipt or existing
   create-only marker. If selecting the unchanged standalone short-E defaults,
   bind its own path/hash instead. No parameter may become a new CLI override.
4. Run the packet's 11 isolated stdlib tests with CUDA hidden, low CPU affinity and
   niceness. Check the deployed copy's shared hash and wrapper identity separately
   from repository evidence. Obtain independent review of the exact future packet
   and source closure, including the three variant values. Prior source review is
   evidence, not a review of a new authorization or a different endpoint.
5. Before any later launch, the existing owner revalidates its exact identities,
   STOP/PAUSE controls, captured descendants and canonical GPU/IO inode/descriptor
   custody through the established controller. Preserve its no-overwrite checks,
   deadlines, private process sessions and natural boundary handoff. This source
   simplification supplies no alternative ownership or scheduling mechanism.
6. Preserve incomplete return code 3 only for arena attempts; prepare, CPU export,
   progress, final readback and adjudication still require success. Continue to bank
   the existing source/manifest/inference and paired receipts. Make no strength or
   performance claim from source simplification or CPU contract tests.

Recovery is through existing reviewed controller behavior. Retain the original
source packet and controls; a failed new preparation does not justify editing the
armed packet or retrying a failed operation automatically. After any future launch
has completed or been separately closed by its owner, a different future launch
may select the original adapters in another fresh output/packet. No mid-run source
swap, reset, pin rewrite or automatic rollback is part of this procedure.

Unresolved adoption prerequisites: a future authorized run, available pinned
historical dependencies, exact reviewed source closure and owner admission. No
prerequisite is resolved by publishing this evidence bundle.
