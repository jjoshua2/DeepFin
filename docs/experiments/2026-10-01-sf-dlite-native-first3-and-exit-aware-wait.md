# D-lite native pair: first three sealed manifests and a future exit-aware wait

The first three sealed run03 native control/candidate pairs contain 19,526 selected legacy rows. Their published JSON receipts and file manifests list 24,837,435 bytes across both arms. This readout checks **manifest arithmetic only**: it read three pair receipts and six per-arm manifest JSONs, with no Zarr payload read, decoded-array comparison, archive scan, GPU work, or physical-I/O lease. The full native-pack audit determines whether the pairs are usable for training. See the [D8 label operations record](2026-09-30-sf-dlite-d8-label-operations.md) for the separate label provenance.

The manifests assign 24,626,674 bytes, or 99.1514% of the two-arm listed file bytes, to fields other than the main `search_wdl` target. That is a **logical field-size fraction**. The producer reports matching decoded non-main raw digests, but this JSON-only readout did not verify those arrays. Across the already compressed files, only 91,403 bytes (0.3680% of the two-arm total) have both matching per-path SHA and size and thus qualify as *listed* one-copy candidates before payload rehash. These are neither measured disk savings nor a proposed in-place hardlink operation: changing published chunks would invalidate the existing manifests.

Each pair has 52 differing compressed-chunk hashes: 13 each in `x`, `policy_target`, `legal_mask`, and the deliberately changed `search_wdl`. The three non-main fields have equal listed per-path sizes despite differing hashes. All `.zarray` and root metadata entries match by listed SHA. The JSONs do not establish whether the chunk differences arise from encoding, data, or another cause; they establish neither corruption nor decoded parity. The control manifests list 12,396,422 chunk bytes and 22,302 metadata bytes, with candidate chunk bytes 12,396,409 and the same metadata total. Their combined 1,272.019 listed bytes per selected row are specific to this narrow legacy sample, not a 500M corpus compression ratio, allocated-block measurement, or forecast.

The [compact arithmetic evidence](evidence/sf-dlite-native-first3-exit-aware-20261001/first3-manifest-arithmetic.json) preserves the three receipt and six manifest SHAs, counts and per-field mismatches without host paths. It was derived from the frozen nine-JSON arithmetic source SHA-256 `ad44191adfcb9b9417838232a6aacd4e20210a5dfb3a3d07f9528e92f3562e66`. Next, the independent whole-pack audit must verify every published file and decoded control/candidate field. Only after that qualification could a separate encode-once candidate be compared on a bounded real shard, including build/compression/fsync time, allocated blocks and both-arm reader parity. The live run03 writer and manifests remain unchanged.

The run03 builder also exposed a possible scheduling cost: in its first 20 published pairs, sampled build units ended at 10.036–10.060 seconds and verify units at 5.013–5.030 seconds, with roughly five-second sampling intervals. The child completion times were not observed, so this trace does not measure removable idle time. A frozen future source candidate replaces only the final `sleep(5)` in `run_unit` with `process.wait(timeout=5)` and returns to the same watchdog checks on `TimeoutExpired`. The 30 other top-level functions, fresh-exec child guard, caps and exception cleanup stay byte/AST-equivalent to the reviewed v12 baseline. This patch is **archival**, not a live run03 change or an adopted builder.

In isolated CPU child fixtures, an immediate successful child took 5.0151 seconds with the baseline poll and 0.0725 seconds with the candidate. The candidate's long child remained sampled at approximately five-second intervals; exit-7, test-only deadline and memory-floor cases held with no surviving child. The independent review reran all six cases and reported `SOURCE_CPU_PASS_ONLY_NO_LIVE_ADOPTION`. These observations measure fixture notification latency, not pack throughput or a realized 384-shard speedup. The [sanitized CPU evidence](evidence/sf-dlite-native-first3-exit-aware-20261001/exit-aware-wait-cpu.json) pins the candidate, baseline, unchanged guard and independent-review SHA-256 `7920479bb9245ef383a9e8fce6999c964681d4010845adc494a8c8f98122f84d`; the [archival patch](evidence/sf-dlite-native-first3-exit-aware-20261001/exit-aware-wait.patch) is SHA-256 `f4c28548e4371d84dce0a46236bb0dc2f560a8942804b7c930b6471e75c3fb02`. Any future builder adoption needs a separately reviewed source pin and real bounded run after the active writer finishes.
